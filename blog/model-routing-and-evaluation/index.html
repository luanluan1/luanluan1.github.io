小模型先走、大模型兜底：路由之前先建立评测

模型路由不能只依赖模型自报信心。应从业务风险出发，建立节点指标、升级条件和可观测记录。

  • 模型路由
  • 评测
  • 可观测性
  • Agent

“先调用小模型，小模型觉得不行再调用大模型”听起来能省成本，但其中最不可靠的部分是“小模型觉得”。语言模型生成的置信分数不一定经过校准，写出 0.93 不代表它真的有 93% 的正确概率。

先按节点拆模型，而不是整个 Agent 只选一个模型

一个 AI 应用可以在不同节点使用不同能力：

节点 适合先尝试的方案 需要升级的信号
意图分类 小模型或分类模型 类别接近、出现未知意图、高风险业务
日期与金额提取 规则加小模型 格式校验失败、字段冲突、缺少必要参数
向量检索 Embedding 模型 召回证据不足或多个版本冲突
判断与回答 大模型 需要跨文档推理、证据矛盾或任务风险高
退款执行 确定性后端代码 不交给模型自由决定

模型大小不是唯一变量。规则、结构化输出、检索质量和工具接口设计，常常比直接换更大模型更有效。

升级条件要来自可验证信号

比“模型自评分低于 0.9”更可靠的信号包括：

  • 分类概率的第一名和第二名差距过小。
  • JSON Schema 校验不通过。
  • 日期、金额与订单数据库记录不一致。
  • RAG 没有召回足够证据，或证据相互矛盾。
  • 输入属于退款、权限变更等高风险类别。

阈值不能凭感觉固定成 0.9。它应在验证集上测试：不同阈值分别会漏掉多少错误、增加多少成本和延迟，再按业务损失选择。

指标要能定位具体环节

只看最终“用户是否满意”，无法判断问题是出在检索、分类还是工具执行。可以分层观察：

层级 典型指标
意图与抽取 分类准确率、字段 Exact Match、必填字段完整率
RAG Recall@K、证据精确率、引用正确率、回答忠实度
工具 调用成功率、参数校验失败率、幂等冲突率、未知状态率
端到端 任务完成率、人工介入率、P95 延迟、单任务成本

精准正确率和任务完成率并不相同。系统可能召回了很多内容，用户仍然完成任务；也可能引用非常准确，却因为流程中断而没有完成业务目标。两者都要测。

用户反馈是线索，不是标准答案

点赞、差评和文字反馈适合发现测试集没有覆盖的问题。但用户可能误解制度，也可能只因答案不合预期而打低分。

问题进入修复前，应先归因：

意图分类错误
检索未召回
召回证据错误
模型脱离证据回答
工具参数或权限错误
外部系统失败

不同原因对应不同修复。分类错误可以补样本、改提示词或换模型；检索错误应检查切片和召回；工具状态错误不能靠提示词解决。

上线时先影子测试，再逐步替换

新模型可以先读取真实流量但不影响用户结果，记录它与旧模型的差异，这叫影子测试。确认效果后，再把少量流量切给新模型，逐步扩大范围。

日志至少记录模型版本、Prompt 版本、脱敏后的输入、结构化输出、工具错误、引用 chunk_id、延迟和成本。银行卡号等敏感信息不应直接进入日志；需要时用掩码、代号或受控查询替代。

也不需要保存模型完整的隐藏思考过程。更适合审计的是可验证的决策摘要、证据引用、规则命中和工具状态。
