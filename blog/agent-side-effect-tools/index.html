从“调用成功”到“业务可靠”：Agent 的副作用工具

当 Agent 能够退款、建单或发送通知时，超时、重试和并发会让一次简单调用变成状态管理问题。

  • Agent
  • 幂等
  • 状态机
  • 后端可靠性

我最初对 Agent 工具的理解很直接：模型收集参数，用户确认，调用退款接口，然后根据返回值回复。这条链路在 Demo 中没问题，但在生产环境里，最危险的恰恰是那些“没有明确返回值”的情况。

超时不等于失败

请求超时时，只能确定客户端没有在规定时间内收到响应，不能确定对方没有处理。

一次退款请求可能已经被支付平台受理，只是回包在网络中丢失。如果系统把超时标记为失败，然后用新的业务编号再发起一次，就可能产生两笔退款。

因此退款状态不只有成功和失败，至少还需要：

pending -> processing -> succeeded
                      -> failed
                      -> unknown

unknown 表示外部系统的真实结果暂时无法确定。此时不应告诉用户“退款失败，请重试”，而是使用原业务编号查询平台状态。

幂等键要保持稳定

可以在调用外部平台前创建唯一的 refund_id，并在所有重试中继续使用它：

refund_id: RF202608040001
order_id: ORDER123
status: pending
provider_status: unknown

唯一编号本身不等于完整的幂等。数据库需要唯一约束，支付平台也需要识别这个编号，或者提供状态查询能力。如果外部平台两者都不支持，代码就无法严格保证“只执行一次”。

查询后更新不是原子操作

两个 Worker 都可能先查到 pending，然后同时执行退款。安全的抢占需要把条件和更新放在同一条数据库语句里：

UPDATE refunds
SET status = 'processing'
WHERE refund_id = :refund_id
  AND status = 'pending';

只有影响行数为 1 的 Worker 才获得执行权。其他 Worker 看到影响行数为 0，应立即停止。

Agent 不是真实状态的来源

模型可以识别意图、收集参数和解释结果，但不应决定退款是否真正成功。最终输出应由持久化的业务状态决定：

  • succeeded：可以告知用户退款成功。
  • failed：只能在有明确拒绝结果时输出失败。
  • pending / processing / unknown：只能输出处理中，并继续查询或转人工对账。

这个问题让我重新划分了 Agent 的责任：模型负责理解和表达，确定性代码负责权限、状态和副作用。
