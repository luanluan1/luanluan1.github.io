LangChain 与 LangGraph：从调用组件到控制业务流程

固定 Pipeline、状态图、人工确认、失败补偿和上下文记忆分别解决什么问题，以及它们如何组合。

  • LangChain
  • LangGraph
  • 工作流
  • 状态管理

我最初容易把 LangChain 和 LangGraph 当成两个需要二选一的框架。更准确的理解是：LangChain 偏向提供模型、Prompt、检索器和工具调用等组件，LangGraph 偏向控制这些组件以什么状态、顺序和分支运行。

先判断任务是否需要“记住执行到哪一步”

如果流程总是从上到下执行，失败就结束，普通代码或固定 Pipeline 已经足够：

识别意图 -> 提取参数 -> 校验格式 -> 调用查询 -> 生成回答

当流程出现以下要求时，状态图更合适：

  • 需要根据结果走不同分支。
  • 需要暂停等待用户确认或人工审核。
  • 工具超时后要查询状态，再决定是否重试。
  • 进程重启后要从上次成功节点继续。
  • 部分步骤失败后，要执行补偿操作。

LangGraph 的价值不只是把节点画成图，而是把业务状态持久化，让系统知道“已经完成什么、下一步允许做什么”。

请假流程可以保持固定，但状态要明确

一个请假 Agent 可以使用稳定的主流程：

收集请假类型和日期
  -> 查询剩余假期
  -> 展示可编辑确认单
  -> 创建请假申请
  -> 发送通知

它的状态不应只存在聊天文本里，可以单独记录：

{
  "request_id": "LEAVE202608040001",
  "user_id": "USER123",
  "leave_type": "annual",
  "start_date": "2026-08-10",
  "end_date": "2026-08-11",
  "confirmed": true,
  "status": "processing",
  "completed_steps": ["validated", "confirmed", "created"],
  "error_code": null
}

固定流程和 LangGraph 并不冲突。Pipeline 描述正常路径，Graph 负责分支、暂停、恢复和异常路径。

失败不一定要撤销前面所有操作

“通知发送失败”不等于“请假申请创建失败”。如果申请已经被审批系统受理，直接删除申请再重跑，反而可能制造重复数据。

更安全的处理是按业务语义决定：

  • 可重试：通知使用稳定的 notification_id 重试。
  • 可补偿：确实需要撤销时，调用明确的取消申请接口。
  • 不可自动恢复：保留已完成状态和错误原因，转人工处理。

补偿操作是另一个明确的业务动作，不是数据库意义上的“时间倒流”。它本身也需要权限、幂等和审计。

对话上下文不等于业务状态

模型支持长上下文，只表示它能读取更多文字，不表示它可靠地保存了业务状态。

通常可以分成三层：

  1. 最近若干轮原始对话，用于理解代词和当前话题。
  2. 更早对话的结构化摘要，用于控制上下文成本。
  3. 数据库中的业务状态，用于保存确认结果、工具执行状态和幂等编号。

前两层帮助模型理解，第三层才是系统恢复和审计的依据。用户在执行前修改参数，可以更新待确认状态；执行后再补充，应根据已发生的业务结果决定修改、取消或新建，而不是假装第一次调用没有发生。

我的选择规则

  • 单次问答、检索和简单工具组合：先用普通代码或 LangChain 组件。
  • 固定且短的业务流程：使用显式 Pipeline，并把参数校验写在确定性代码里。
  • 有分支、暂停、重试、恢复和人工介入：使用 LangGraph 一类状态图。
  • 涉及退款、建单、通知等副作用：无论用什么框架，都必须单独设计幂等、权限和状态查询。

框架解决的是编排方式，不会自动替我补齐业务可靠性。
