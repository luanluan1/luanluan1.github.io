我以前把 RAG 想得很简单。用户提问，系统去向量数据库里找几段文本，再把文本交给模型。整理企业知识库的检索过程以后，我发现一次查询要经过几种不同的判断。

有些问题依赖整体语义，例如“收入为什么减少”和“营收下滑的原因”应该互相找到。有些问题又必须把词找准，例如订单号、产品型号和客户名称。单一路径很难同时照顾这两种情况，所以生产 RAG 通常把召回、融合、精排和生成拆开。

```text
用户问题
   ↓
BM25、Sparse Vector、Dense Vector 并行召回
   ↓
RRF 合并多路排名
   ↓
Reranker 重新判断候选内容
   ↓
保留少量片段
   ↓
LLM 根据片段生成答案和引用
```

## Dense Vector 负责找相近的意思

Embedding 模型会把问题和文档片段转换成固定长度的数值向量。系统再用余弦相似度等方法比较它们的距离。

```text
问题：销售额下降  → [0.12, -0.38, 0.75, ...]
文档：营收下滑    → [0.10, -0.35, 0.72, ...]
```

向量的大部分维度都有数值，所以叫稠密向量。它擅长处理近义表达，也不要求问题和文档使用完全相同的词。自然语言问答、制度查询和产品说明通常都需要这类召回。

Dense 的短板也很明显。订单号、型号和精确数字在向量空间里没有稳定的特殊待遇，语义相近的片段还可能被误认为可以回答当前问题。向量每个维度代表什么，通常也很难直接解释。

## Sparse Vector 和 BM25 把词找准

Sparse Vector 的维度通常对应词或 Token，只有少数维度有非零权重。

```text
销售额  0.83
营收    0.61
下降    0.72
2026    0.91
```

它更敏感于术语、实体名称和编号。学习型 Sparse 模型还能根据训练结果扩展相关词，不过扩词效果取决于具体模型和分词方式。

BM25 也偏向关键词匹配，但它依靠词频、逆文档频率和文档长度等统计规则计算分数，不需要神经网络模型。它和学习型 Sparse Vector 都适合下面这类查询。

```text
订单号：SO20260018
产品型号：K3-WISE-15.1
客户名称：广州某某公司
```

两者的区别可以这样记。

| 对比 | BM25 | 学习型 Sparse Vector |
| --- | --- | --- |
| 权重来源 | 词频、逆文档频率和文档长度 | 模型学习得到的 Token 权重 |
| 语义扩展 | 通常没有 | 可能具备 |
| 精确关键词 | 强 | 强 |
| 模型依赖 | 不依赖神经网络模型 | 通常依赖专用模型 |
| 解释方式 | 可以回看词频和匹配词 | 可以查看 Token 及权重 |

实际项目里，我会保留 BM25，再根据数据规模和模型条件加入 Sparse Vector。Dense 和关键词检索各自解决一类问题，不能只看其中一路的效果。

## RRF 只负责合并排名

三种召回会产生三份排行榜。

```text
Dense              Sparse             BM25
1. 文档 A          1. 文档 C          1. 文档 D
2. 文档 B          2. 文档 A          2. 文档 A
3. 文档 C          3. 文档 D          3. 文档 C
```

这些检索器的原始分数不能直接相加。Dense 的相似度可能是 `0.82`，BM25 的分数可能是 `15.7`，数值范围和含义都不同。

RRF，也就是 Reciprocal Rank Fusion，只看每篇文档在各路结果中的名次。

```text
RRF_score = Σ 1 / (k + rank)
```

一篇文档在多份榜单中都靠前，就会得到较高的融合分数。RRF 不读取问题和文档内容，也不需要额外的语义模型，速度快，适合把多路召回先合成一份候选名单。

## Reranker 重新阅读候选片段

Reranker 接收用户问题和一条候选片段，输出它们的相关性分数。

```text
问题 + 文档 A  → 0.95
问题 + 文档 C  → 0.82
问题 + 文档 D  → 0.21
```

它会同时阅读问题和候选内容，判断这段文字是否真的能够回答问题。常见实现采用 Cross-Encoder，精度通常高于只比较两条独立向量的相似度。

Reranker 不能一开始就阅读整个知识库。每条候选都要单独计算问题与片段的关系，候选数量一多，延迟和成本都会上升。常见做法是先用 BM25、Sparse 和 Dense 快速召回 20～100 条，再交给 Reranker 精排，最后留下 5～10 条。

RRF 和 Reranker 的位置不同。RRF 处理多份排行榜，Reranker 处理问题与候选内容的关系。前者负责把名单合在一起，后者负责重新判断名单里的顺序。

## LLM 负责根据资料回答

LLM 读取最终保留的片段、用户问题、必要的历史对话和工具结果，然后生成自然语言或结构化答案。它可以做总结、推理和引用组织，不能替代前面的召回评估。

让 LLM 给几十条候选逐条打分当然可以，但每条内容都要占用模型调用成本，分数也更容易受提示词和上下文顺序影响。专用 Reranker 更适合批量重排，LLM 放在最后处理少量已经筛过的资料。

## 权限要在资料进入模型前完成

企业知识库还有一个容易被忽略的条件。片段即使语义相关，当前员工也可能没有阅读权限。

文档切片入库时，应把文档 ID、版本、租户、部门和授权信息写进每个片段的元数据。查询时先根据用户身份生成过滤条件，再执行召回。缓存命中时同样要用当前权限重新过滤，不能只相信缓存创建时的权限快照。

在候选已经进入 Reranker 以后再过滤，可能浪费计算，也可能因为日志、缓存或异常路径把无权内容继续传给模型。权限过滤应当是检索过程的硬条件，引用输出还要带上文档版本和原文位置。

## 一条企业 RAG 流程

```text
数据源同步
   ↓
文档解析、清洗、切片并写入权限元数据
   ↓
建立 BM25、Sparse Vector 和 Dense Vector 索引
   ↓
根据租户、部门和用户权限生成过滤条件
   ↓
三路并行召回
   ↓
RRF 合并，保留 30～100 条候选
   ↓
Reranker 精排，保留 5～10 条片段
   ↓
LLM 根据片段生成答案
   ↓
返回答案、Chunk ID、文档版本、页码和原文链接
```

这里的顺序有两个原因。召回阶段需要快，所以适合用索引和并行查询。精排阶段需要认真读内容，所以只处理已经缩小的候选集。生成阶段再把少量可靠资料放进模型上下文，控制 Token 和错误引用。

## 从什么参数开始测试

下面的数字只能作为第一轮实验的起点，不能直接当成生产结论。

| 环节 | 测试起点 |
| --- | --- |
| 每路召回 | 30～50 条 |
| RRF 融合后 | 30～100 条 |
| Reranker 最终保留 | 5～10 条 |
| 权限过滤 | 召回前执行，缓存命中后再次执行 |
| 引用字段 | 文档 ID、Chunk ID、标题、页码、版本、原文链接 |

评测时要把检索和回答分开看。可以先用人工标注的问题集测试每个问题应该命中哪些片段，再测 RRF 和 Reranker 是否把这些片段排到前面，最后看 LLM 是否依据这些片段回答并给出正确引用。

我现在会这样记这几个概念。

| 组件 | 主要工作 |
| --- | --- |
| BM25 | 按原文关键词、词频和文档长度查找 |
| Sparse Vector | 按重要 Token 和可能的扩展词查找 |
| Dense Vector | 按整体语义查找 |
| RRF | 合并多路搜索排名 |
| Reranker | 重新判断问题和候选片段的相关性 |
| LLM | 根据最终资料推理并生成答案 |

RAG 的质量不只取决于模型大小。切片是否合理，关键词和语义召回是否互补，权限是否在正确位置过滤，Reranker 是否留下了能回答问题的片段，都会影响最终答案。下一步更值得做的是拿真实业务问题建立评测集，再决定每一路召回和重排要保留多少内容。
