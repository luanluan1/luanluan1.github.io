> 系列总纲 [如何构建一个 Agent](/posts/how-to-build-an-agent/)

总纲把 Agent 拆成任务、上下文、模型、工具、状态、安全和验证七层。这一篇只看上下文。

模型每次决定下一步以前，都要先知道用户想做什么，当前任务进行到哪里，上一轮工具返回了什么。知识库 Agent 还要找到相关制度或产品文档，代码 Agent 则要从项目里找到可能相关的文件。Runtime 把这些信息挑出来，组成模型这一轮实际能看到的输入。

## 上下文层装了哪些信息

常见内容可以分成四组。

| 内容 | 解决的问题 | 例子 |
| --- | --- | --- |
| 固定规则 | Agent 被允许怎样工作 | System Prompt、项目规范、权限要求 |
| 当前任务 | 用户现在要什么 | 当前问题、已确认参数、验收条件 |
| 外部知识 | 模型原本不知道什么 | RAG 文档片段、代码、数据库查询结果 |
| 执行状态 | 前面已经发生了什么 | 工具返回、错误信息、完成步骤 |

这些内容的可信程度不同。数据库中的订单状态可以决定退款结果，模型根据对话生成的摘要只能帮助理解。项目规范能够提醒 Agent 运行测试，Runtime 还要强制限制危险操作。

上下文也有成本。一次放入太多文件会占用上下文窗口，无关内容还可能干扰模型。Agent 通常先检索和过滤，再读取少量候选内容。

## RAG 是上下文来源之一

RAG 的入库部分继续整理在 [RAG 入库先做什么，文档解析与切片的边界](/posts/rag-document-parsing-and-chunking/)，检索部分继续整理在 [RAG 检索与重排，从海选到答案](/posts/rag-retrieval-reranking-core-concepts/)。

需要查询企业制度、客服知识或产品文档时，RAG 很常见。它通常分成入库和查询两个阶段。

文档入库时，系统先切分文本，为每个 Chunk 生成向量，再保存正文、向量和权限元数据。文档新增或更新时重新处理对应部分，无需在每次提问时把所有文档重新计算一遍。

用户查询时，系统为当前问题生成一个向量，从向量数据库召回少量 Chunk，完成权限过滤和可选的重排，再把结果交给大模型。

```text
用户问题
  ↓
生成查询向量
  ↓
按权限和版本过滤
  ↓
召回相关 Chunk
  ↓
可选的 Rerank
  ↓
相关内容进入模型上下文
```

Agent 可以通过一个检索工具使用这套服务。

```python
chunks = knowledge_base.search(
    query=user_question,
    user_id=user_id,
    top_k=5,
)

answer = llm.generate(
    question=user_question,
    context=chunks,
)
```

Embedding 模型可以运行在云端，也可以作为本地服务。Agent 只关心检索工具返回了哪些内容，以及这些内容是否带有来源、版本和权限信息。

## 普通电脑能不能运行 RAG

文档入库阶段计算较多。系统要为每个 Chunk 生成向量，第一次建立索引会花一些时间。查询阶段只需要处理一条问题，并在索引中寻找相似向量，计算量小得多。

向量占用空间可以粗略计算。十万个 `768` 维 `float32` 向量的原始大小约为

```text
100000 × 768 × 4 字节 ≈ 307 MB
```

实际系统还要保存索引、正文和元数据。几千到几万个 Chunk 可以在普通开发电脑上运行，速度还会受到 Embedding 模型、索引类型和 CPU 性能影响。数据达到几十万或上百万，并且同时需要高并发、复杂权限和重排时，可以把 Embedding 与向量数据库拆成独立服务。

使用云端 Embedding API 时，向量计算发生在服务端，本地负责发送文本和保存结果。这样降低了本地硬件要求，也带来了调用费用、网络依赖和数据合规问题。

RAG 能减少传给大模型的文档数量，也会引入切片、召回和权限过滤方面的误差。知识库上线前要单独评测召回率，回答正确率无法替代检索评测。

## 代码 Agent 经常先用精确搜索

代码里有大量明确符号。函数名、接口路径、错误码和配置键都可以直接搜索。代码 Agent 因此常用 `rg`、AST 和 LSP 获取上下文。

这三种工具的理解范围不同。

| 工具 | 能理解的内容 | 常见用途 |
| --- | --- | --- |
| `rg` | 文件中的文字 | 搜索关键词、错误码和接口路径 |
| AST | 代码的语法结构 | 查找函数调用、分析或修改语法节点 |
| LSP | 跨文件引用和类型语义 | 跳转定义、查找引用和检查类型 |

它们主要使用普通 CPU。Agent 先用这些工具缩小范围，再让大模型阅读相关代码，可以减少 Token 消耗。

## `rg` 完成快速文本搜索

`rg` 的全名是 ripgrep，可以把它理解成命令行里的项目全局搜索。

```powershell
rg -n "refundOrder" src tests
```

这条命令会在 `src` 和 `tests` 中查找包含 `refundOrder` 的文本，并显示行号。Agent 可以先找到候选位置，再读取相关文件。

`rg` 只认识文本。注释、函数定义和普通字符串里出现同一个词时，都会被搜出来。搜索错误码、接口路径和函数名时，这种能力通常已经够用。

## AST 让程序看见语法结构

AST 是抽象语法树。解析器会把源代码拆成有层级的语法节点。

```ts
const total = price * count;
```

解析后的结构大致是

```text
变量声明
├─ 变量名 total
└─ 乘法表达式
   ├─ price
   └─ count
```

AST 能区分变量声明、函数调用和字符串字面量。工具可以只查找对某个函数的调用，也可以批量修改满足特定结构的代码。注释里出现同一个单词，不会被当成函数调用处理。

AST 主要描述语法结构。跨文件导入、变量实际指向哪个定义、接口由哪些类实现，还需要类型系统和语言服务器参与。

## LSP 提供跨文件语义

LSP 是语言服务器协议。编辑器里的跳转到定义、查找所有引用、类型提示和重命名，很多都通过它完成。

```ts
import { refundOrder } from "./refund";

await refundOrder("ORDER123");
```

文本搜索可以找到 `refundOrder` 出现过的位置。LSP 还能判断这次调用来自哪个文件，参数类型是什么，项目中还有哪些地方引用了同一个函数。

它接近编辑器平时使用的代码理解能力。对于大型项目，跨文件的定义和类型信息往往比单纯搜到一个同名字符串更有用。

## 一次代码检索怎样组合这些工具

面对登录接口报错，Agent 可以先用 `rg` 搜索接口路径和错误信息。找到候选文件后，再通过 LSP 追踪函数定义与调用关系。需要识别某类语法或批量修改时，AST 工具继续处理。模型最后阅读筛选后的代码，判断原因并制定修改方案。

```text
用户描述错误
  ↓
rg 找到候选文件
  ↓
LSP 追踪定义、引用和类型
  ↓
AST 识别需要处理的语法结构
  ↓
模型阅读相关代码并决定修改
  ↓
测试、构建和差异检查
```

语义比较模糊时，也可以加入向量检索。用户只记得项目里“有一套任务恢复机制”，却不知道函数名，Embedding 有机会找到含义接近的文档或代码片段。已经知道精确符号、错误码或路径时，文本搜索与语言工具通常更直接。

面试里讲上下文层，可以从选择检索方式开始。知识库查询适合 RAG，代码符号优先使用 `rg`、AST 和 LSP，工具返回继续进入下一轮上下文。Runtime 负责过滤权限和控制长度，模型只读取与当前任务相关的内容。
