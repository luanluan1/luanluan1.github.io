> [系列总览与完整目录](/posts/codex-enterprise-agent-control-plane/)

一个 Agent 工作台很容易出现几种不同的成功。API 接单了，模型回答结束了，文件生成了，原测试通过了，外部写入也许完成了。它们需要各自的证据。一条“任务完成”消息无法解释全部环节。

项目的验证和交付因此按层推进。这里把前面各篇的实现放回实际开发过程，说明测试做到了哪里，哪些人工反馈改变了产品，以及部署更新怎样保留原数据。

## 自动验证分几类证据

| 验证方式 | 实际使用的组件 | 主要回答的问题 |
| --- | --- | --- |
| 协议与单元测试 | 受控输入、假时钟和传输替身 | 超时、校验、状态转换和消息边界是否符合契约 |
| API 与数据库测试 | 真实 HTTP 和隔离 PostgreSQL | 权限、幂等、并发锁、版本和事务是否生效 |
| 容器与运行时测试 | 真实 Docker、固定 Codex、免费 provider | 命令、停止、续聊、工具和文件是否真正执行 |
| 浏览器契约测试 | 真实页面资源，部分接口使用替身 | 控件、草稿、焦点、迟到响应和布局是否正确 |
| 浏览器集成测试 | 页面、真实 API、数据库和测试运行链路 | 用户操作能否走到实际记录与交付结果 |
| 真实模型样例 | 受控 DeepSeek 任务 | 特定真实提示词在当时是否完成工作 |
| 人工反馈 | 使用者实际操作与材料 | 真实效果、理解成本和体验是否符合需要 |

例如，模拟接口的 MCP 编辑测试可以证明修改端点后页面要求重填凭据，却不能独立证明 Token 加密存储。后者需要检查真实 API、数据库密文和错误返回。

免费 provider 会返回预设模型动作，让固定 Codex 实际运行命令或请求工具。这能重复触发故障，不产生供应商费用；模型该不该提问、能否理解复杂材料，则留给真实模型和人工场景。

## 最新一批检查具体覆盖了什么

截至 2026 年 10 月 26 日，能力中心批次的本地单测为 74 项，其中 11 项涉及远程 MCP 传输。这个数字不包含全部浏览器和集成探针，也不能与历史各批测试数相加当成独立用例总量。

远程完整链路使用真实 TLS、数据库、浏览器和固定 Codex 运行物。个人 Agent 发起工具请求，管理员批准，平台调用 HTTPS 服务，结果回到原任务并交付报告。

另一条链路让服务在收到调用后断开连接，检查工具和任务进入待核实，清理扫描不会再创建第二个 Run。连接中撤权则直接检查外部写入为零。这里观察的是动作和数据，页面文案只是附加结果。

该批 PR 的九组 CI 作业包括仓库检查、运行时、工作台页面、OIDC、文件交付、配额、治理、对话及会话文件。九组作业通过后合并到 main，仍不将待反馈的人工作为已通过填写。

## 几个真正影响实现的缺陷

| 发现的问题 | 为什么会发生 | 修复与验证 |
| --- | --- | --- |
| 关闭审批后抛错，旧审批又出现 | 状态更新随事务错误一起回滚 | 先提交关闭与拒绝审计，再返回拒绝，验证同键重试 |
| 等待数据库锁后仍按旧时间批准 | 请求进入时有效，拿到锁时已过期 | 锁后读数据库时钟，用真实锁等待验证 |
| 成员快速恢复后旧任务可能继续 | 单次轮询看不到中间撤权 | 撤权事务保存停止意图，恢复不清除 |
| 杀掉宿主连接，任务仍在写文件 | attach 进程与容器子进程不是同一生命周期 | 停整个容器，观察 PID 和文件增长 |
| Excel 字面编号被当成转义串 | 表格格式对特定字符串有特殊解释 | 保存后读回单元格与表名，验证字面值 |
| 旧组织的预览响应迟到 | 页面切换早于网络请求返回 | 身份、组织和请求代次核对，清空过期内容 |

这些问题分别出现在数据库、运行环境和格式交付上。给前端多加一个 loading，无法替代对应层的修复。

独立审查与自行运行测试也分别记录。只读审查可以指出一条错误路径，实际探针才证明本次执行的结果；局部独立复核不扩写成全系统安全认证。

## 人工测试改了哪些产品细节

前批外部测试保留过五项问题或建议。七种文件上传后没有显示实际大小；错误附件移除后旧错误仍残留；首次登录回调偶发失败；测试报告的汇总口径把部分通过误写成全部失败；历史详情区需要独立滚动。

其中附件反馈和滚动问题复用原有状态与 CSS 修复。报告问题需要以新生成结果复测，不能直接修改旧验收产物掩盖历史。登录偶发问题则需要服务端时间线，单凭截图不足以判断根因。

后续还有输入框过大、成员权限选项难理解和添加候选重复等反馈。对应改动分别收紧 composer、把权限转为业务访问级别，以及在数据库过滤候选后分页。自动化回归保留这些行为，人工再集中关注新功能和真实任务质量。

这样安排减少了朋友反复执行同一批清单的成本，但没有取消人的验收。尚未操作的项目继续标记待反馈，不能用自动测试结果替他补上通过。

## 本机部署由哪些部分组成

平台使用本机持久化 PostgreSQL，身份服务使用独立 Keycloak 数据卷。Runner 创建任务容器，持续对话保留工作卷和 Codex 会话卷；回收执行容器不删除身份或对话文件。

宿主 Node 和运行镜像固定版本。Windows 守护入口负责当前用户登录后的启动和有限故障恢复，仍依赖 Docker 与用户环境。它没有成为无登录服务器服务，也没有跨节点高可用。

需要外部测试时，应用和身份服务的公开 origin、issuer、回调和 Cookie 策略必须一致。TCP 穿透只负责转发连接，不会自动解决证书或登录回调。相关 HTTPS 和身份契约用隔离实例验证，公网是否可用仍取决于电脑、Docker 和穿透服务状态。

## 更新为什么先检查任务和备份

当前本机进程依赖检出的代码目录。部署更新先检查在途任务，停止接单和相关服务，再保存数据库及必要私有状态，应用迁移，重启并检查页面。不能为了修复服务启动，重新初始化账号或重置额度。

能力中心迁移前保存数据库备份，更新后比较了 21 张业务表原有字段的行数与摘要，检查已有账号、历史与用量保留，原文件卷继续存在。这里证明的是这次本机更新的数据一致性。

完整恢复另有独立实验。冷备包含业务数据库、身份数据、工作卷与会话卷，归档校验路径、摘要及资源映射；恢复到新数据库和新资源，避免演练与原实例共享工作卷。恢复本身不启动付费任务。

验证继续使用真实 Codex 恢复原线程并修改原文件，再检查原实例文件和额度不变。损坏归档、缺卷和映射不匹配需要拒绝。这与“数据库备份命令返回成功”是不同范围的证据。

## 稳定性改进与仍未查清的部分

守护程序曾把相隔数小时的故障累计进同一重启预算，导致后续恢复停止。后来改为连续健康一段时间后补充预算，短暂成功不清零，待机后的探测给予有上限的恢复窗口。

诊断又把当前健康检查与最后历史事件分开，避免服务已经恢复，界面仍因旧事件显示异常。测试使用可控制时钟，再结合真实 HTTP、进程和隔离数据库验证。

此前底层进程异常退出仍没有完整定位。守护能够拉起服务，只证明恢复路径起作用，不能据此宣称掉线根因已经解决。长期待机、负载和第二台机器验证仍继续保留。

## 后续工作的顺序

第一步是用真实办公材料验证输入到交付，记录材料特征、预期结果和错误，而非继续扩大通用页面数量。第二步选择一家具体 MCP，核对它的认证、Schema 和业务幂等能力。模型效果与外部写入都需要真实场景约束。

跨主机恢复和长期运行应形成独立验收，覆盖账号、证书、域名及凭据迁移。只有出现明确的多节点需求，再考虑队列服务、共享凭据设施和发布回滚机制。

框架引入也遵循相同顺序。需要复杂分支或可持久化等待，再评估 LangGraph 的内部编排；需要第二种运行时，再扩展 Adapter 契约。企业业务状态、授权和文件归属已有明确位置，可以围绕真实需求逐步替换。

这组记录对应的成果，是一条可以实际操作和验证的企业 Agent 工作流程，以及能够解释失败与权限变化的工程实现。它为后续试用提供了基础，生产可靠性和业务效果仍需要后续证据。
