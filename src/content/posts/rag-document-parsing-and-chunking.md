我把 RAG 的检索、重排和生成理顺以后，又遇到一个更靠前的问题。知识库里的 Chunk 到底从哪里来。

很多系统把文件上传、解析、切片和建索引放在一个按钮后面。使用者看见的是“解析完成”，程序实际做了好几件事。PDF 里的文字要先恢复成正确的阅读顺序，表格要保留行列关系，标题要和正文建立层级，之后才适合决定哪些内容组成一个可检索片段。

这几步可以先这样分开。

```text
原始文件
  ↓
文档解析，恢复文字、版面、表格、图片、公式和阅读顺序
  ↓
结构化结果，包含标题、段落、表格、页码和坐标
  ↓
切片，决定哪些内容组成一个 Chunk
  ↓
BM25、Sparse Vector、Dense Vector 建立索引
  ↓
检索、融合、重排和生成
```

MinerU 和 RAGFlow DeepDoc 主要处理前两步。固定长度、标题层级、条款、表格行和父子块等方法，处理的是后面的切片。

## 为什么拿到文件以后不能马上切

PDF 内部保存的通常是字符、文本块和坐标。它未必保存了人眼看到的自然段，也未必按阅读顺序排列。

```text
人眼看到
第三章 采购管理

3.1 采购申请
采购人员应当填写采购申请单……
```

程序直接提取后，可能得到这样的顺序。

```text
采购人员 第三章 3.1 应当填写
采购管理 采购申请 采购申请单
```

双栏排版会把左右两栏交错，页眉页脚会混进正文，浮动图片会离开图注，跨页表格也可能被截成两张互不相干的表。切片算法收到的输入已经错了，后面换 Embedding、Reranker 或 LLM 只能在错误的文字上继续计算。

所以解析阶段至少要恢复这些关系。

- 页面和栏目的阅读顺序
- 标题与正文的层级
- 段落和列表的边界
- 表格的行、列与合并单元格
- 图片和图注的关系
- 页码、坐标和原文位置
- 公式与特殊符号

切片是在这些关系已经可用以后，重新决定检索单元的大小。

## OCR 只回答图片里写了什么

扫描 PDF、手机拍照和没有文本层的图片，需要先做 OCR。OCR 的任务是把图像中的字符识别出来，通常还会返回文字在页面上的坐标。

坐标能说明文字出现在哪里，OCR 本身却不知道这段文字是标题、正文还是表格单元格。它也无法单独决定多栏页面应该先读哪一栏。

因此，OCR 是解析流程的一部分。得到一批文字之后，还要把它们放回页面结构中。

## 版面识别和表格识别补上页面结构

版面识别会给页面区域分类。常见区域有标题、正文、列表、表格、图片、图注、页眉页脚和公式。它还要判断不同区域之间的阅读顺序。

表格结构识别通常叫 TSR。它要恢复单元格的行列位置、合并单元格、多级表头，以及跨页表格之间的关系。表格里的文字全部识别正确，单元格关系错了，金额仍然可能被配到错误的客户。

文档解析因此是一个更大的概念。

```text
原生文本提取
      + OCR
      + 版面识别
      + 阅读顺序恢复
      + 表格结构识别
      + 图片和图注提取
      + 公式识别
      + 清洗
```

HTML 通常可以直接利用 DOM、标题标签和表格节点。Word、PPT 和 Excel 则可以结合文件本身的段落、形状、幻灯片和单元格结构。PDF 是最难处理的一类，因为它更像一组排版指令，文件里未必保留作者写作时的段落结构。

## MinerU 负责把复杂文件变成结构

MinerU 是独立的文档解析项目。当前官方仓库列出的输入包括 PDF、图片、DOCX、PPTX 和 XLSX，输出可以是 Markdown、JSON 以及带版面信息的中间结果。它还处理扫描件、多栏内容、跨页表格、图片、图注、公式和页眉页脚。

对 RAG 来说，MinerU 的价值在于先把文件转成下游程序看得懂的结构。例如一份采购制度经过解析，可以得到这样的结果。

```markdown
# 第三章 采购管理

## 3.1 采购申请

采购人员应当填写采购申请单。

| 字段 | 是否必填 |
| --- | --- |
| 供应商 | 是 |
```

这个 Markdown 已经比 PDF 的字符坐标更适合继续处理，但它还没有自动决定最终的 RAG Chunk。下游仍要判断标题是否需要带入正文，表格是整块保存还是按行拆分，条款之间是否要保留父级标题。

MinerU 可以作为独立解析服务，输出交给自建切片程序、LangChain、LlamaIndex 或其他知识库系统。它的解析层和后续索引层可以分别替换，适合需要保存中间结果、做人工抽检或接入多个下游系统的团队。

## DeepDoc 是 RAGFlow 内部的文档理解组件

RAGFlow 的 DeepDoc README 把它分成 vision 和 parser 两部分。它为 PDF、DOCX、Excel 和 PPT 提供相应的解析器，PDF 解析结果可以包含带页面和矩形坐标的文本块、表格以及带图注的图片。

这使 DeepDoc 和 RAGFlow 的知识库页面连接得很紧。解析结果可以继续进入 RAGFlow 的切片、关键词索引和向量索引流程，原文定位和页面高亮也有数据可以依靠。

RAGFlow 的界面把解析和切片放在同一条入库流程里，使用者容易把它们当成一个动作。实际过程仍然可以拆开理解。

```text
DeepDoc 解析
  ↓
RAGFlow 的切片模板重新组织内容
  ↓
生成最终 Chunk
  ↓
建立全文和向量索引
```

General、Manual、Paper 等名称更多是在描述下游怎样组织内容。它们不能替代 OCR、版面分析和表格结构恢复。

## MinerU 与 DeepDoc 怎样区分

| 对比 | MinerU | RAGFlow DeepDoc |
| --- | --- | --- |
| 主要角色 | 独立文档解析器 | RAGFlow 内置文档理解组件 |
| 处理内容 | OCR、版面、表格、图片、公式和阅读顺序 | OCR、版面、表格、图片和阅读顺序 |
| 结构化输出 | Markdown、JSON 和中间结果 | 供 RAGFlow 后续流程使用的文本块、表格和位置数据 |
| 与切片的关系 | 解析后交给下游策略 | 解析结果继续进入 RAGFlow 的切片模板 |
| 适合的场景 | 解析层独立部署，多个系统共用 | 使用 RAGFlow 的知识库和检索流程 |

把它们只当成两种 OCR，会漏掉最重要的差别。两者都在恢复文档结构，解析器的输入输出、模型依赖和后续接法才是选型时需要比较的内容。

## 同一种切片策略也会得到不同结果

假设两个解析器都采用“按标题切片”。解析器 A 得到的是完整的标题和正文。

```text
标题：实验方法
正文：完整的方法内容……
标题：实验结果
正文：完整的结果内容……
```

解析器 B 把双栏内容交错了。

```text
实验方法第一行
实验结果第一行
实验方法第二行
实验结果第二行
```

两边使用相同的切片代码，B 的 Chunk 仍然无法回答完整问题。可以用一个近似关系提醒自己。

```text
最终效果 ≈ 解析质量 × 切片质量 × 检索质量 × 生成约束
```

这个式子不是评测公式，它只说明错误会层层传下去。解析质量接近零时，后面再精调 Chunk 长度，改变的只是错误内容的大小。

## 解析器和切片策略可以怎样组合

### RAGFlow 一体化使用

```text
文件
→ DeepDoc
→ RAGFlow 切片模板
→ 全文和向量索引
→ 混合检索与重排
```

这条路线适合希望快速搭建知识库、需要可视化查看 Chunk，并且不打算单独维护解析服务的团队。

### MinerU 加自建 RAG

```text
文件
→ MinerU Markdown 或 JSON
→ 自定义清洗和切片
→ BM25、Sparse Vector、Dense Vector 索引
→ RRF、Reranker 和 LLM
```

这条路线适合需要保存原始解析结果、加入业务条款规则，或者让多个应用共用同一套解析服务的团队。

### MinerU 接入 RAGFlow

RAGFlow 的发布记录曾加入 MinerU PDF 解析选项，具体是否可用还取决于 RAGFlow 版本、部署方式和相应模型配置。接入时要检查三件事。

- MinerU 输出的标题、位置和图片关系是否被完整传入
- RAGFlow 是否会再次重组已经正确的逻辑块
- 最终 Chunk 是否保留页码、坐标、版本和引用信息

不要只看 MinerU 输出的 Markdown 是否好看。RAGFlow 最终交给检索器的 Chunk 才是要评测的对象。

## 哪些步骤需要模型

| 环节 | 常见实现 |
| --- | --- |
| 原生文本提取 | 文件解析库 |
| OCR | OCR 模型 |
| 版面识别 | 专用视觉模型或 VLM |
| 表格结构识别 | 专用模型或 VLM |
| 标题和编号识别 | 样式、正则或版面模型 |
| 固定长度和标题切片 | 确定性代码 |
| 语义断点切片 | Embedding 模型 |
| LLM 辅助切片 | 通用 LLM |
| 图片描述、关键词和摘要 | 视觉语言模型或 LLM |

“用 AI 解析”不等于“每个 Chunk 都让 LLM 决定”。固定规则更容易重复，成本也更可控。复杂的表格、图表和语义边界，可以在抽样或特定文档类型上使用模型增强。

## 拿到一批文件以后先判断什么

我会按这个顺序检查。

1. 文件有可用的文本层吗，还是必须 OCR。
2. 页面里有没有多栏、跨页表格、图片和公式。
3. 解析后的阅读顺序是否正确。
4. 标题、正文、页眉和页脚是否区分开。
5. 用户问题的最小完整答案单位是什么。
6. 再选择标题、条款、固定长度、表格行或父子块策略。
7. 用真实问题测试最终 Chunk 的 Top K 召回。

这条顺序能避免一个常见误区。刚开始就纠结 `512` 还是 `800` Token，实际上是在调节切片长度，解析顺序和表格关系还没有确认。先打开几个最终 Chunk 看看，再决定参数，通常更省时间。
