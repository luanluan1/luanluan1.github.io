> 上一篇 [RAG 入库先做什么，文档解析与切片的边界](/posts/rag-document-parsing-and-chunking/)

把文件解析成文字以后，RAG 还有一个很容易被低估的决定。哪些内容应该放在同一个 Chunk 里。

这个决定会影响三个地方。Embedding 看到什么，检索能不能命中，模型拿到片段以后能不能完整回答。Chunk 太小，条件和结论会被拆开。Chunk 太大，主题被稀释，检索结果还会占掉更多上下文。

RAGFlow 提供了 General、Manual、Paper、Book、Laws、Presentation、Table、Q&A、One、Picture、Tag 等内置模板，企业版还提供 Resume。它们对应不同的文档结构和答案单元。模板名称可以帮助选起点，最终效果仍然要用真实问题评测。

本文先讲通用切片方法，再看这些模板怎样组合解析器、边界信号、合并函数和元数据。RAGFlow 的版本会继续变化，文中涉及源码的地方以 2026 年 8 月 `main` 分支为参照。

## 先定义什么叫好 Chunk

一个可用的 Chunk，至少要同时满足这些条件。

- 用户的问题有机会从里面召回关键词、实体或语义表达。
- 答案中的条件、结论和限定词没有被拆到别的片段。
- 片段离开原文以后，仍然知道所属的产品、章节、条款或业务对象。
- 长度足够让 Embedding 表达主题，也不会吞掉过多模型上下文。
- 文件、版本、标题路径、页码、坐标和来源链接能够被追溯。

因此，切片应当围绕“最小完整答案”设计。一个 FAQ 可能只有三行，一个法律条款可能需要带上完整父条款，一张产品表又适合按业务对象拆开。

## 常见的切片方法

### 固定长度

按照字符数或 Token 数从前往后切分，通常再加一点重叠。

```text
Chunk 1：Token 1 到 500
Chunk 2：Token 451 到 950
Chunk 3：Token 901 到 1400
```

它简单、稳定、适用于各种纯文本，适合先做一版基线。缺点也很直接，句子、列表和章节可能在中间断开。长度和重叠比例需要用评测集调整，不能从一个通用数字推导出所有业务的答案。

### 递归边界

递归切片会依次尝试较粗到较细的边界。

```text
章节标题
  ↓
段落
  ↓
换行
  ↓
句号和分号
  ↓
字符
```

只有当前单元仍然太长，才继续向下拆。它比固定位置更容易保留自然段，常用于通用文本切片。它仍然看不懂标题之间的业务关系，遇到制度条款和表格时需要额外规则。

### 句子和段落

先按句子或段落切开，再把相邻单元合并到目标长度。文本自然，调试也容易。只靠标点无法判断标题级别，适用条件和处理方法也可能被分到两个 Chunk。

### 标题层级

利用 Markdown 标题、Word Heading、HTML 标题或版面识别结果建立标题路径。

```text
采购管理
  └─ 采购申请
       └─ 创建申请
```

正文带上完整路径以后，即使被单独召回，模型也知道它属于哪个章节。产品手册、SOP、技术文档和制度文件通常适合从这个方法开始。

### 编号和条款

法规和公司制度的结构经常由 `第一章`、`第十二条`、`1.1.2`、`（一）` 这些编号表达。编号本身也是引用线索，父条款、子项和限定条件应当保持在可以追踪的关系里。

### 页面和幻灯片

以 PDF 页面或 PPT 幻灯片为边界，保留页面文字、图片和页码。它适合一页讲一个主题的课件，也方便回答“第几页写了什么”。跨页连续叙述的长文档使用这种边界时，需要额外补标题和上下文。

### 表格行

表格可以把每一行改写成带表头的自解释记录。

```text
产品编码：P001；产品名称：减速机；单价：5600；状态：在售
```

这种形式适合产品参数、客户字典和设备清单。涉及求和、同比、筛选和分组时，优先使用数据库或分析工具，RAG 只负责找到字段定义和说明。

### 问答对

把一个问题和标准答案放在同一个 Chunk 中，检索时提高问题字段的权重。

```text
问题：采购入库单审核后能否修改？
答案：已审核单据需要先反审核，才可以修改……
```

FAQ、客服知识和售后话术适合这样处理。问题列要覆盖用户真实说法，否则仍需 Dense 检索或同义问题增强。

### 父子块

父块保留完整章节，子块负责精确命中。

```text
父块：完整章节，约 1000 Token
子块：章节中的小段，约 200 Token
```

检索先使用子块，命中以后把父块或相邻上下文交给模型。这样可以同时照顾召回精度和回答所需的上下文。父子块会增加索引和拼接逻辑，权限、版本和引用关系也要一起维护。

### 语义边界

为连续句子生成 Embedding，观察相邻内容的语义变化，在变化较大的位置切开。它能处理没有清晰标题的资料，代价是需要额外计算，阈值也比较敏感。编号、表头和法条之间的关系，仍然要由规则保护。

### LLM 辅助

可以让 LLM 判断主题边界、补标题、写摘要或生成问题。高价值、结构混乱的少量资料可以这样增强，全部文件交给 LLM 自由切分则会带来成本、延迟、复现和版本变化问题。

实际项目通常让确定性规则完成基础切片，再把模型用在标题补全、关键词、问题生成和图片描述上。

### 多模态块

正文、图片、图注和表格可以组成一个检索单元。系统需要保存媒体对象，并用 OCR、视觉语言模型或表格解析器生成可检索描述。重要图表的原图和结构化数值应当同时保留，视觉描述不能替代精确数据。

## RAGFlow 模板在解决什么问题

RAGFlow 的配置文档把“解析文件”定义成两个连在一起的动作。先根据文件布局生成 Chunk，再在这些 Chunk 上建立向量和全文索引。界面把两步放在同一条流程里，源码仍然使用不同解析器和切片函数完成它们。

当前官方文档列出的模板与支持格式大致如下。

| 模板 | 主要结构信号 | 常见格式 |
| --- | --- | --- |
| General | 分隔符和 Token 长度 | Markdown、DOCX、XLSX、PPT、PDF、TXT、图片、CSV、JSON、EML、HTML |
| Q&A | 问题和答案字段 | XLSX、CSV、TXT |
| Resume | 简历字段和结构 | DOCX、PDF、TXT，企业版 |
| Manual | 目录、标题、页面位置 | PDF |
| Table | 表头、数据行和列类型 | XLSX、XLS、CSV、TXT |
| Paper | 标题、作者、摘要和章节 | PDF |
| Book | 长篇标题层级和长度回退 | DOCX、PDF、TXT |
| Laws | 章节、条款和子项编号 | DOCX、PDF、TXT |
| Presentation | 页面或幻灯片 | PDF、PPTX |
| Picture | OCR 和图片描述 | JPEG、JPG、PNG、TIF、GIF |
| One | 整个文件 | DOCX、XLSX、XLS、PDF、TXT |
| Tag | 内容和标签字段 | XLSX、CSV、TXT |

这里的映射是理解用的简化版。实际处理还会受到文件解析器、租户配置、模型提供方和当前版本影响。

## General 适合先做基线

General 的主要思路是连续拿到段落、表格和图片，再按照分隔符和目标 Token 数进行合并。它关注长度和顺序，较少强制解释某种文件结构。

```text
解析文件
  ↓
得到连续文本和媒体
  ↓
按分隔符拆出候选单元
  ↓
顺序合并到目标长度
  ↓
生成文本块和媒体块
```

普通 Word、Markdown、HTML 和结构较规整的文本 PDF，可以用 General 建立第一版基线。它也适合拿来和专用模板做对照。

常见风险是相邻章节被合并，或者一个完整操作被长度边界拆开。标题是否被带入正文，还取决于前面的解析结果和清洗规则。

## Manual 关注操作步骤

Manual 主要面向产品手册和操作文档。当前实现会综合 PDF 目录、标题编号、页面位置、Word 标题级别、表格和图片上下文。PDF 分支还会经过 OCR、版面分析、表格分析和文本合并。

它适合 ERP 手册、API 使用指南、设备维护手册和有可靠目录的 SOP。一个理想的结果类似下面这样。

```text
库存管理 > 采购入库 > 审核入库单
进入采购入库列表，选择待审核单据……
```

Word 没有使用真正的 Heading 样式，或者 PDF 目录和正文不一致时，程序只能退回编号和版面启发式判断，标题路径可能不完整。

## Paper 先保护论文结构

Paper 会优先处理标题、作者、摘要和章节，并把表格作为独立内容处理。论文、研究报告和技术白皮书适合使用它。

它的专用结构也带来边界。非标准论文、参考文献和扫描版报告可能让标题识别不稳，第三方解析器输出的逻辑块也可能和 DeepDoc 不同。评测时要单独查看摘要、方法、实验和参考文献是否被正确区分。

## Book 面向长篇资料

Book 适合教材、培训资料、长篇报告和多章节书籍。当前源码会尝试清理目录，识别部分标题形式，检测编号体系。识别到结构时使用层次合并，结构不明显时回退到普通 Token 合并。

```text
第五章 检索系统 > 5.2 向量检索
HNSW 通过多层图结构加速近邻查询……
```

长书不应该默认整本入库。先限定有效页码，再检查章节层级和引用位置，通常更容易得到稳定结果。

## Laws 保护条款关系

Laws 针对法规、合同、公司规章和政策文件。它识别章节、条款和子项编号，再把内容组织成树形关系。

```text
员工考勤管理办法 > 第三章 请假管理 > 第十二条
员工请假应当提前三个工作日提交申请……
```

条款编号还能帮助定位原文。只按段落切开，容易把“适用范围”“例外情况”和“处理时限”拆散。Laws 会尽量让父条款、子项和限定条件一起进入检索和引用。

它仍然依赖编号质量。文档里的编号混乱、表格承载条款，或者一个条款跨越多个版面时，需要人工查看最终 Chunk。

## Presentation 以页面为答案单元

Presentation 以页面或幻灯片为天然边界。它适合培训课件、产品演示和汇报材料。

```text
第 8 页：区域销售分析
华南区本季度销售额同比增长 18%……
```

纯文本很少的图表页需要额外做图表解析或视觉描述。跨页讲一个连续结论的课件，则要把前后页标题和页码带入上下文。

## Table 让每一行变得自解释

Table 按工作表、表头和数据行处理，当前文档还提到 TSI 技术和列类型推断。它适合产品参数、客户字典、设备清单和静态编码表。

```text
产品编码：P001；名称：减速机；额定功率：15kW；状态：在售
```

表头必须有明确业务含义。多行表头、合并单元格和空列要先清洗。经营明细的统计分析应当走数据库或分析工具，Table 更适合查找记录和字段说明。

## Q&A 把问答当成一个单元

Q&A 适合 FAQ、客服话术和售后问答。Excel、CSV 和 TXT 中的问答列可以直接组成问题与答案，标题路径也可以在某些文档中承担问题的作用。

```text
问题：如何重置密码？
答案：进入个人中心的安全设置……
```

多个问题堆在一个单元格里，会让一个 Chunk 同时对应多个意图。问题的写法也要覆盖用户实际会说的词，必要时补充同义问题。

## One 只适合真的很短的文件

One 将整个文件作为一个 Chunk。短公告、完整声明、产品卡片和不允许拆开的短知识适合使用它。

大文件使用 One 会让 Embedding 的主题变得模糊，召回也更难精确，还可能超过模型的上下文限制。完整并不自动代表更好，关键在于文件本身是否就是一个答案单元。

## Picture 处理图像知识

Picture 会对图片执行 OCR。在文字不足时，当前实现还可能使用视觉语言模型生成描述，再把图片、文字和描述交给后续索引。

它适合海报、扫描图片、产品图片、流程图和图示。小字、精确数字、箭头关系和复杂图表容易在视觉描述中丢失，重要内容应当保留原图，并另外抽取结构化字段。

## Tag 是检索辅助字典

Tag 数据通常由内容和标签组成。标签进入独立字段以后，可以用于分类、路由和检索增强。

```text
内容：K/3 WISE 15.1
标签：金蝶，ERP，本地部署，财务软件
```

它更适合产品线、行业、部门、业务域和同义词字典。标签库应当和正文知识分开管理，避免把一串分类词误当成完整业务说明。

## Resume 适合结构化简历资料

Resume 是 RAGFlow 文档中列出的企业版模板，适用于 DOCX、PDF 和 TXT。它的目标是把个人信息、教育背景、经历、技能等字段组织成便于检索的结构。

简历检索经常同时要求匹配技能、年限和项目经历。只保留连续文本，可能让技能和对应项目脱离。使用 Resume 时，应检查字段是否被正确识别，并确认个人信息的访问权限和脱敏要求。

## 模板差异来自五个地方

同一个文件换一个模板，Chunk 数量和边界可能完全不同。差异通常来自五个层面。

### 输入解析器

PPT 使用幻灯片解析，Excel 使用工作表解析，PDF 可以选择 DeepDoc、Naive、MinerU、Docling 或其他解析器。解析器输出的段落、坐标、表格和图片关系，会直接影响后续切片。

### 边界信号

- General 看分隔符和长度。
- Manual 看目录、标题和页面位置。
- Laws 看章节和条款编号。
- Presentation 看页面。
- Table 看表头和数据行。
- Q&A 看问题和答案字段。

### 合并函数

源码中可以看到几类合并思路。

- `naive_merge` 按顺序累加到目标 Token。
- `hierarchical_merge` 按标题或编号层级组织内容。
- 条款策略先建立树，再输出父子关系。
- 页面策略保留页面边界。
- 表格策略把表头与数据行组合起来。

具体函数和字段会随版本调整，阅读源码时要以当前分支为准。

### 元数据

标题路径、页码、坐标、表格类型、图片、问题和标签都会影响过滤、关键词检索、引用和页面高亮。正文看起来完整，元数据丢失以后，检索和引用仍然可能退化。

### 回退规则

结构识别失败时，有些模板会回退到普通长度合并，有些模板仍坚持按页面、数据行或整文输出。第三方解析器还可能关闭默认长度合并，尽量保留解析器返回的逻辑块。

## 一段内容换模板会怎样

原文如下。

```text
第三章 采购管理
3.1 创建采购申请
申请人选择供应商并填写数量。

3.2 审核采购申请
金额超过十万元时由总经理审核。
```

同一段内容可能得到这些结果。

| 策略 | 可能的结果 |
| --- | --- |
| 固定长度 | 在 Token 边界拆开，可能跨越 3.1 和 3.2 |
| General | 按段落和长度合并，两个小节可能在同一个 Chunk |
| Manual | 生成两个操作小节，并带上“采购管理”父标题 |
| Laws | 把编号识别为条款层级，保留父子关系 |
| Q&A | 将标题当作问题，正文作为答案 |
| One | 整份文件只有一个 Chunk |

这些模板都没有凭空理解业务。它们使用不同的结构信号，让“十万元是审批条件”更有机会与对应的小节留在一起。

## 怎么选择起点

| 内容类型 | 首选 | 检查重点 |
| --- | --- | --- |
| 普通文档 | General | 标题是否被带入，段落是否完整 |
| 操作手册和 SOP | Manual | Heading、目录和步骤边界 |
| 法规、制度和合同 | Laws | 长条款、例外和子项 |
| 论文和研究报告 | Paper | 摘要、正文和参考文献 |
| 书籍和长教材 | Book | 有效页码和章节层级 |
| PPT | Presentation | 图表页和跨页结论 |
| FAQ | Q&A | 一个问答一个块 |
| 产品参数表 | Table | 表头能否独立解释数据 |
| 短公告 | One | 文件是否真的足够短 |
| 图片资料 | Picture | OCR、数字和图表关系 |
| 标签词典 | Tag | 标签是否和正文职责分开 |
| 简历资料 | Resume | 字段识别、隐私和脱敏 |

拿不准时，可以让 General 作为基线，再用一个更贴近资料结构的模板做对照。两套结果要放到同一组真实问题上比较，不能只看 Chunk 数量或页面展示是否整齐。

## 参数怎么起步

下面的数值只能作为测试起点。

| 场景 | 可测试的起点 |
| --- | --- |
| 普通制度 | 400 到 700 Token，约 10% 重叠 |
| 操作手册 | 250 到 500 Token，保留标题路径 |
| 法律条款 | 一条一个父块，长条款再建子块 |
| FAQ | 一个问答一个块，通常不重叠 |
| 长篇报告 | 父块 800 到 1500，子块 150 到 300 Token |
| 表格 | 一行或一个业务对象一个块 |

RAGFlow 的模板不一定都按同一个方式使用 `chunk_token_num`。结构策略可能优先遵守章节、页面或数据行边界，第三方解析器还可能尽量保留自己的逻辑块。界面上的 Token 数不能单独预测最终 Chunk。

## 上线前怎样评测

我会先从真实业务中整理 30 到 100 个问题，并给每个问题标出正确文件、页码和原文位置。随后按下面顺序检查。

1. 查看解析后的阅读顺序、标题和表格。
2. 查看最终 Chunk 是否带着完整答案和限定条件。
3. 测试 Top 5 和 Top 10 是否命中正确片段。
4. 记录命中排名和引用位置。
5. 把解析失败、切片失败和检索失败分开统计。
6. 更换模板后，用同一批问题重新比较。

建议至少保存这些字段。

```text
问题
标准答案所在文件和页码
期望 Chunk
Top 5 是否命中
命中排名
失败环节
```

如果一个问题的答案在原始解析结果里已经被打乱，先修解析器或清洗规则。解析结果完整，最终 Chunk 缺少标题和条件，再调整切片。只有 Chunk 合理而 Top K 仍然找不到时，才继续检查 Embedding、关键词召回、权限过滤和重排。

## 结尾

固定长度、标题层级、条款、页面、表格行、问答对和父子块，都是可以迁移到不同 RAG 系统的通用方法。RAGFlow 的模板把这些方法和对应的解析器、合并函数、元数据及回退规则组合起来，方便针对资料类型选择入库路线。

模板名称只适合用来选起点。切片需要保留完整答案、限定条件、权限和引用位置。上线评测要检查真实问题能否稳定找到可追溯的答案单元。
